corrija y genere el módulo de código para auditarlo'. Hoy ese proceso

Para ejecutar acciones concretas, el Orchestrator se comunica vía protocolo
MCP con dos servidores de habilidades: uno que sabe hablar con la API de
NexaPlay, y otro que sabe generar código. Esos servidores corren como
subprocesos aislados usando stdio, no como servicios HTTP independientes.
Eso elimina puertos, autenticación y descubrimiento de servicios.

Y arriba de todo, la API de Claude: Sonnet para razonar y planificar, Haiku
para resumir. Cada tarea usa el modelo correcto para ese trabajo.

Criterio evaluado: Calidad técnica + trade-offs de diseño

[IDE CON ÁRBOL DE CARPETAS ABIERTO EN PANEL IZQUIERDO.
El árbol debe mostrar: specs/, src/agent/, src/skills/, src/tests/]

GUION HABLADO:

"Déjenme mostrarles la estructura del proyecto y las decisiones de diseño
que tomé — incluyendo qué alternativas consideré y por qué las descarté.

[SEÑALAR specs/ en el árbol sin hacer clic todavía]

Empiezo por aquí: el archivo specs/nexaplay-openapi.yaml. Este es el
contrato OpenAPI de la API de NexaPlay. Es la fuente de verdad del sistema.
El agente lo lee como un recurso MCP — el servidor de habilidades lo expone
bajo el URI 'nexaplay://openapi-spec'. Antes de ejecutar cualquier plan,
el agente tiene acceso al contrato completo. Eso es lo que le permite saber
qué endpoints existen, qué parámetros son requeridos, y qué esperar en las
respuestas.

[SEÑALAR src/agent/ en el árbol]

Este es el núcleo del agente. Hay cinco componentes principales:

[ABRIR orchestrator.py — mostrar la función `run` y el loop principal]

El Orchestrator es el director de orquesta. Su único trabajo es coordinar:
llama al planner para generar el plan, luego itera sobre los pasos
ejecutándolos, y al final llama al summarizer. Lo importante aquí es que
está diseñado para ser extensible: los métodos _on_step_start, _on_step_result
y _call_tool son hooks que el RichOrchestrator del CLI sobreescribe para
agregar la UI visual. La lógica de negocio no se mezcla con la presentación.

[TRADE-OFF A MENCIONAR AQUÍ:]
'Consideré meter la presentación dentro del orchestrator directamente —
es más simple al principio — pero eso habría hecho imposible testear
la lógica de negocio sin capturar output de consola. Separar los hooks
permite testar el orchestrator con mocks simples sin tocar el CLI.'

[SEÑALAR o abrir planner.py brevemente]

El Planner le pide a Claude Sonnet que convierta el requerimiento en un plan
JSON estructurado. Cada paso declara la herramienta, el propósito, los inputs,
y una precondición. Las precondiciones son expresiones que el runtime evalúa
en tiempo de ejecución. Por ejemplo: 'ejecutar el POST solo si
$step1.data.operational_limit es menor que $step1.data.min_allowed'.
El agente no asume resultados, los lee primero.

[SEÑALAR o abrir model_router.py brevemente]

El ModelRouter decide qué modelo Claude usar para cada tipo de tarea. No es
hardcodeado: planificación usa Sonnet con temperatura cero porque necesita
ser determinista. Generación de código usa Sonnet con temperatura también
cero, porque queremos código reproducible. Summarización usa Haiku porque
es más económico y no necesita el razonamiento profundo de Sonnet. Y todo
es configurable por variable de entorno sin tocar una línea de código.

[TRADE-OFF A MENCIONAR AQUÍ:]
'Podría haber usado Sonnet para todo — más simple de mantener. El costo
es real: Haiku cuesta aproximadamente 25 veces menos que Sonnet por token.
Para un job con resúmenes frecuentes en producción, eso importa. La
separación de responsabilidades en el ModelRouter hace que este trade-off
sea ajustable sin tocar el código de negocio.'

[SEÑALAR o abrir context_manager.py brevemente]

El ContextManager resuelve un problema real en jobs largos: si el agente
ejecuta muchos pasos, las observaciones acumuladas pueden desbordar la
ventana de contexto de Claude. Este componente mantiene solo las últimas 3
observaciones en ventana activa. Las más antiguas las comprime a una sola
frase con Haiku antes de descartarlas. Así el costo en tokens permanece
acotado independientemente del tamaño del job.

[SEÑALAR src/skills/ en el árbol]

Las habilidades son servidores MCP completamente independientes. El servidor
nexaplay_api expone la herramienta nexaplay_api_call. Internamente, usa
un cliente HTTP con retry automático, backoff progresivo de 1, 2 y 4
segundos, y una idempotency-key determinística basada en SHA-256 del
job_id más el número de paso. Eso garantiza exactamente una escritura aunque
la red falle y el agente reintente.

[TRADE-OFF A MENCIONAR AQUÍ:]
'La alternativa era un circuit breaker completo. Lo descarté porque el
agente ya tiene un límite de pasos por job y un detector de loops — agregar
un circuit breaker habría sido redundancia sin beneficio real para el
volumen esperado. Si el caso de uso escala a miles de jobs concurrentes,
ese sería el siguiente paso natural.'

[SEÑALAR src/skills/codegen/ brevemente]

El servidor de codegen expone code_generator. Llama a Claude Sonnet con
el contexto técnico real de la API como input, genera código y test unitario,
valida la sintaxis con ast.parse, y si falla, reintenta una sola vez con el
error de sintaxis como contexto. Honesto en vez de silencioso: si el segundo
intento tampoco funciona, el campo summary lleva el prefijo [UNVALIDATED]
en vez de mentir que el código es válido.

[SEÑALAR src/tests/ brevemente]

Y la suite de tests cubre todo esto: unit tests por skill, tests del cliente
HTTP con mocks de red via respx, tests de integración del orchestrator
completo con mocks de MCP y Anthropic. Más de diez archivos de test
independientes. El criterio de diseño fue: cada componente testeable en
aislamiento, sin depender de red real ni de Claude en los tests unitarios."

[PAUSA. Abrir terminal. Transición al demo.]

================================================================================
PREGUNTAS QUE EL EVALUADOR PROBABLEMENTE VA A HACER
(prepárate para responderlas si el video incluye Q&A)
================================================================================

P: ¿Por qué stdio y no HTTP para los servidores MCP?
R: Stdio elimina puertos, autenticación y descubrimiento de servicios. Para
   habilidades que corren en la misma máquina o container, es más simple y
   más seguro. HTTP tendría sentido si las habilidades necesitaran escalar
   de forma independiente en pods separados.

P: ¿Qué pasa si el plan generado por Claude tiene un paso que no existe
   como herramienta disponible?
R: El Orchestrator valida cada paso contra la lista de herramientas antes
   de ejecutarlo. Si el tool no existe, el paso falla con TOOL_NOT_FOUND
   y el job se detiene. El planner recibe la lista real de herramientas
   disponibles antes de generar el plan, así que esto es poco probable,
   pero la validación existe como capa de defensa.

P: ¿Por qué Pydantic para validar el plan y no simplemente JSON schema?
R: Pydantic da validación con mensajes de error descriptivos que podemos
   devolver directamente al modelo en el retry del planner. JSON schema
   puro requeriría un paso adicional para formatear el error. El modelo
   usa ese mensaje para corregir el JSON en el segundo intento.

P: ¿Cómo escalarías esto si hubiera 500 jobs simultáneos?
R: El cuello de botella principal sería el rate limit de la API de Anthropic.
   Los pasos siguientes serían: cola de jobs con prioridad, pool de workers
   async, y caché de planes para requerimientos repetidos. La arquitectura
   actual no necesita cambios estructurales para eso — se puede poner un
   worker pool encima del Orchestrator sin tocar su lógica interna.

P: ¿Los tests pasan en CI?
R: Sí. Los unit tests usan mocks de red (respx) y mocks del cliente Anthropic,
